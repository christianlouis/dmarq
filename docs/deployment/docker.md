# Docker Setup

Docker Compose is the recommended way to run a single-host DMARQ instance. The
default stack pulls the tested `docker-stable` image from GHCR, starts PostgreSQL
on an internal network, and publishes DMARQ only on
`127.0.0.1:8080`.

The bundled Compose database defaults to PostgreSQL 17 (`postgres:17-alpine`).
DMARQ's database code and migrations are tested against PostgreSQL 16, 17, and
18. PostgreSQL 14 was retained from the original Compose stack; it was not a
DMARQ application requirement, and its final upstream release was November 12,
2026. PostgreSQL 16, 17, and 18 remain supported upstream ([versioning policy](https://www.postgresql.org/support/versioning/)).

## Prerequisites

- Docker Engine 24 or later
- Docker Compose v2.20 or later (`docker compose version`)
- Linux AMD64 or ARM64 host
- OpenSSL
- Python 3.10 or later for `scripts/verify-docker-compose.sh`
- 2 GB RAM minimum, 4 GB recommended
- 20 GB free storage

## Quick Start

Run these commands from a new checkout:

```bash
git clone https://github.com/christianlouis/dmarq.git
cd dmarq
./scripts/bootstrap-docker-env.sh
docker compose pull
docker compose up -d --wait
```

The bootstrap script creates `.env` from `.env.example`, generates stable
application, API, and database secrets, and never prints those values. Open
[http://localhost:8080](http://localhost:8080) after both containers are
healthy.

For unattended setup, use the versioned
[Agentic Installation](agentic-installation.md) contract. `dmarqctl` performs
machine-readable preflight, renders the same Compose environment safely, starts
the published image, and completes first-run setup without a browser.

The default is a local single-user installation:

- DMARQ is bound to `127.0.0.1`, not every network interface.
- PostgreSQL is available only to the application container.
- `AUTH_MODE=disabled` means no DMARQ login is required on that local address.
- Reports and configuration persist in Docker volumes across restarts.

Do not expose this default directly to the internet. Configure an identity
provider or a trusted authentication proxy before changing
`DMARQ_BIND_ADDRESS` to `0.0.0.0`.

## Verify The Installation

```bash
docker compose ps
curl -fsS http://localhost:8080/healthz
curl -fsS http://localhost:8080/api/v1/health
./scripts/verify-docker-compose.sh
```

Both services must be `healthy`. The Compose verification checks the effective
environment, host binding, application port, health check, matching database
identity, and the absence of a published PostgreSQL port.

For a release-grade acceptance test on a new host, follow the
[Greenfield Deployment Verification](greenfield-verification.md) checklist.
Maintainers can run `python3 scripts/verify-greenfield-product.py` on a fresh,
disposable stack to exercise setup, a known DMARC import, exact totals, and
duplicate handling rather than stopping at container health.

## Configuration

Compose reads `.env` in two ways:

1. It uses the PostgreSQL values, host bind address, and host port while
   rendering the stack.
2. It passes the application variables to the DMARQ container through
   `env_file`.

The effective configuration can be inspected without revealing it in an issue
or support transcript:

```bash
docker compose config --quiet
```

Core Docker values are:

| Variable | Purpose | Local default |
|----------|---------|---------------|
| `DMARQ_BIND_ADDRESS` | Host interface that publishes DMARQ | `127.0.0.1` |
| `DMARQ_PORT` | Host HTTP port | `8080` |
| `DMARQ_IMAGE` | Published DMARQ image | `ghcr.io/christianlouis/dmarq:docker-stable` |
| `POSTGRES_DB` | Database created by the Compose PostgreSQL service | `dmarq` |
| `POSTGRES_USER` | Database user created by Compose | `dmarq` |
| `POSTGRES_PASSWORD` | Database password generated by the bootstrap script | generated |
| `DATABASE_URL` | SQLAlchemy connection URL used by DMARQ | generated consistently |
| `SECRET_KEY` | Stable session and credential-encryption key | generated |
| `ADMIN_API_KEY` | Stable key for explicitly authorized API administration | generated |
| `PUBLIC_BASE_URL` | Browser/OAuth base URL | `http://localhost:8080` |
| `AUTH_MODE` | Browser authentication provider | `disabled` |
| `AUTH_DISABLED` | Local no-login mode | `true` |

See [Configuration](configuration.md) for application settings. Optional
mailboxes should normally be added under **Mail Sources** in the web interface.
The legacy `IMAP_*` variables create one initial source only when all required
values are present and no source already exists.

`docker-stable` is the normal installation channel. `docker-latest` tracks a
successfully built `main` branch for preview testing. Production and Kubernetes
operators should prefer an immutable release or short-SHA tag when exact
rollback and auditability matter. Published release, short-SHA, `docker-stable`,
and `docker-latest` tags include Linux AMD64 and ARM64 manifests.

### Build The Checkout Instead

Maintainers and contributors can build the current checkout with the separate
override file. This is not the normal installation path:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml \
  up -d --build --wait
```

### Changing `.env`

`docker compose restart` does not reload environment variables. Recreate the
application container after changing `.env`:

```bash
docker compose up -d --force-recreate --wait app
```

Use `docker compose config` and `docker compose exec app env` to diagnose
effective values. Never paste secret-bearing output into an issue.

## Authentication Modes

For an internet-facing installation, set `AUTH_DISABLED=false`, choose one of
the supported modes, and configure its values:

- `AUTH_MODE=logto`
- `AUTH_MODE=authentik`
- `AUTH_MODE=oidc`
- `AUTH_MODE=trusted_proxy`

Register the callback URL as:

```text
https://your-dmarq-host.example/api/v1/auth/callback
```

Set `PUBLIC_BASE_URL` and the provider-specific redirect URI to the public HTTPS
origin. Production startup blocks an unprotected auth-disabled configuration
unless the operator adds the explicit escape hatch
`ALLOW_AUTH_DISABLED_IN_PRODUCTION=true`.

DMARQ does not currently implement a local username/password browser login. The
owner email on `/setup` is an operational contact, not a login account.

## IMAP transport security

DMARQ uses encrypted IMAP by default. With `Use SSL/TLS` enabled, port `993`
uses implicit TLS (IMAPS) and port `143` uses STARTTLS. Leave this enabled for
hosted mailbox providers.

For a local IMAP bridge that deliberately exposes plain IMAP, such as Proton
Mail Bridge, enter its bridge hostname and port (commonly `143`) and disable
`Use SSL/TLS` in the mail-source form. DMARQ then uses plain IMAP for the
connection test, scheduled polling, manual imports, and backfills. Only use
this mode on an isolated trusted network; DMARQ does not send credentials over
an untrusted cleartext connection.

## Reverse Proxy

Keep the Compose bind address on `127.0.0.1` when Nginx, Caddy, or Traefik runs
on the same host. Proxy to `http://127.0.0.1:8080` and forward the original host
and HTTPS scheme. Example Nginx location:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
}
```

Use TLS and an application authentication mode even when the reverse proxy is
publicly reachable. `AUTH_MODE=trusted_proxy` is valid only when requests cannot
bypass that proxy and it strips spoofed identity headers.

## Mailbox Ingestion

To collect Gmail DMARC reports without a Gmail API OAuth client, add a standard
IMAP source:

| Field | Value |
|-------|-------|
| Method | IMAP |
| Server | `imap.gmail.com` |
| Port | `993` |
| SSL | enabled |
| Username | full Gmail address |
| Password | Google App Password, not the normal account password |
| Folder | `INBOX` or the label/folder that receives reports |

Use **Test connection**, then **Import now**. The connection test counts likely
DMARC messages across common provider subject formats; it does not import or
change mail. DMARQ records every manual and scheduled attempt in import history.
Keep **Delete imported emails** disabled until ingestion and duplicate handling
have been verified.

For older messages, use **Backfill date range**. Progress distinguishes mailbox
messages checked, DMARC reports recognized, new reports, reports already in the
database, unrelated attachments ignored, and actionable warnings. A duplicate-
only run is successful and should report recognized existing reports instead of
claiming that no reports were found.

Scheduled mailbox scans start after the HTTP service is ready and run outside
the request loop. A large inbox must not prevent `/healthz`, the setup flow, or
the browser UI from becoming available after a container restart.

## Update

Back up PostgreSQL first, then:

```bash
git pull --ff-only
docker compose pull
docker compose up -d --wait
curl -fsS http://localhost:8080/healthz
```

Migrations run automatically in the application entrypoint. Do not use
`docker compose down -v` during a normal update; `-v` deletes the database.

#### PostgreSQL major-version changes

Changing the `postgres` image tag is a database major-version migration, not a
normal DMARQ update. Never point a new major-version container at an existing
volume and rely on the container to upgrade it automatically. Before changing
the tag, stop the app, create and verify a custom-format dump, and restore that
dump into a newly initialized volume running the target major version. Keep the
old volume until the restored instance has been checked and the app has started
successfully.

For example, the safe shape of a 14/16/17 to 17/18 move is:

```bash
(
set -eu
docker compose stop app
docker compose exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "dmarq-before-postgres-upgrade.dump"
docker compose exec -T db sh -c 'pg_restore --list' \
  < "dmarq-before-postgres-upgrade.dump" >/dev/null
)
```

Create a separately named target volume and restore into a target container;
keep the original Compose volume untouched until verification succeeds. This
temporary override keeps the target on the Compose network and makes the
volume switch explicit. This example requires Docker Compose v2.24.4 or later
for the `!override` tag. Check the version before stopping the existing
database:

```bash
(
set -eu
compose_version="$(docker compose version --short | sed 's/^v//')"
compose_major="${compose_version%%.*}"
compose_rest="${compose_version#*.}"
case "$compose_rest" in *.*) ;; *) echo "Invalid Docker Compose version: $compose_version" >&2; exit 1;; esac
compose_minor="${compose_rest%%.*}"
compose_patch="${compose_rest#*.}"
case "$compose_major" in ''|*[!0-9]*) echo "Invalid Docker Compose version: $compose_version" >&2; exit 1;; esac
case "$compose_minor" in ''|*[!0-9]*) echo "Invalid Docker Compose version: $compose_version" >&2; exit 1;; esac
case "$compose_patch" in ''|*[!0-9]*) echo "Invalid Docker Compose version: $compose_version" >&2; exit 1;; esac
too_old=0
if [ "$compose_major" -lt 2 ]; then
  too_old=1
elif [ "$compose_major" -eq 2 ] && [ "$compose_minor" -lt 24 ]; then
  too_old=1
elif [ "$compose_major" -eq 2 ] && [ "$compose_minor" -eq 24 ] && [ "$compose_patch" -lt 4 ]; then
  too_old=1
fi
if [ "$too_old" -eq 1 ]; then
  echo "Docker Compose v2.24.4 or later is required (found $compose_version)" >&2
  exit 1
fi
docker compose stop db
docker volume create dmarq_postgres_data_v17
cat > /tmp/dmarq-postgres-target.yml <<'YAML'
services:
  db:
    image: postgres:17-alpine
    volumes: !override
      - dmarq_postgres_data_v17:/var/lib/postgresql/data
volumes:
  dmarq_postgres_data_v17:
    external: true
YAML
docker compose -f docker-compose.yml -f /tmp/dmarq-postgres-target.yml up -d db
ready=0
for attempt in $(seq 1 60); do
  if docker compose -f docker-compose.yml -f /tmp/dmarq-postgres-target.yml \
      exec -T db sh -c 'pg_isready -h 127.0.0.1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'; then
    ready=1
    break
  fi
  sleep 2
done
test "$ready" -eq 1
docker compose -f docker-compose.yml -f /tmp/dmarq-postgres-target.yml exec -T db sh -c \
  'pg_restore --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' \
  < "dmarq-before-postgres-upgrade.dump"
)
```

After checking the target database, stop the temporary target before starting
Compose on that volume, then update the Compose image and volume to match the
override and run `docker compose up -d --wait`. Roll back by stopping the target
and restoring the original image/volume configuration; do not delete the old
volume until the rollback window has expired. PostgreSQL 18's [official image
documentation](https://github.com/docker-library/docs/blob/master/postgres/README.md)
sets `PGDATA` to `/var/lib/postgresql/18/docker`; mount the new volume at the
parent `/var/lib/postgresql` for that target. The PostgreSQL major-version
upgrade itself is an operator/database-administration task; DMARQ only applies
its Alembic migrations after the target database is available.

## Logs And Backups

```bash
docker compose logs --tail=200 app
docker compose logs -f app
```

Create a backup with a fail-closed command group:

```bash
(
set -eu
docker compose exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "dmarq-$(date +%Y%m%d-%H%M%S).dump"
)
```

See [Database Backup and Restore](backups.md) before upgrades or restore work.

## Kubernetes Compatibility

The Compose stack does not change DMARQ's image entrypoint, container port
`8080`, `/healthz` probe, `DATABASE_URL`, or application environment-variable
contract. Kubernetes and GitOps deployments should continue to inject values
through Secrets/ConfigMaps, use a cluster-managed PostgreSQL service if desired,
and pin the released `ghcr.io/christianlouis/dmarq` image. Docker-only variables
`DMARQ_BIND_ADDRESS`, `DMARQ_PORT`, and `POSTGRES_*` are consumed by Compose and
do not need to exist in Kubernetes.

Use the supported [Kubernetes, Helm, and Terraform](kubernetes-terraform.md)
package for new cluster deployments instead of translating Compose manually.

## Troubleshooting

### Browser cannot connect

```bash
docker compose ps
docker compose port app 8080
curl -v http://127.0.0.1:8080/healthz
docker compose logs --tail=200 app
```

### Authentication changes have no effect

Confirm `.env`, then recreate rather than restart:

```bash
docker compose config --quiet
docker compose up -d --force-recreate --wait app
```

### Database is unhealthy

```bash
docker compose logs --tail=200 db
docker compose exec db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Changing PostgreSQL identity variables does not mutate an existing database
volume. For a real installation, migrate or restore the database. Only a
disposable test can be reset with `docker compose down -v`.
